# PRD: RAG 通用建库脚本 — 语义切分 + 父文档检索

- **状态**: Ready for Agent
- **日期**: 2026-06-02

---

## Problem Statement

用户需要将 Markdown 格式的参考文档（如药典、手册、规范）构建为可语义检索的向量知识库。现有工具链存在两个痛点：(1) 固定大小切分破坏文档的语义边界，检索结果碎片化；(2) 缺乏通用的、一次配置即可复用的建库 CLI。用户每次需要针对新文档自行编写切分+入库流水线。

## Solution

一个通用的 CLI 建库脚本，每次只需传入目标 Markdown 文件路径和向量数据库存放目录，自动完成文档解析 → 语义切分 → 向量索引 → Chroma 入库。核心采用**语义切分 + 父文档检索器**模式：利用 Embedding 计算相邻句子相似度找到语义转折点切分（避免在逻辑完整处截断），检索时通过父文档检索器自动返回整节全文（避免碎片化结果）。支持增量更新——已有数据库自动检测新增/变更的节，跳过未修改内容。

## User Stories

1. 作为数据工程师，我希望能用一条命令将 Markdown 文档构建为向量库，只需要指定输入文件和输出目录，其他参数使用合理默认值
2. 作为数据工程师，我希望文档在语义自然转折处被切分，而不是在固定 Token 数处被硬截断，这样每个 chunk 内部逻辑完整
3. 作为数据工程师，我希望切分参数（相似度阈值、重叠句数、最小/最大 chunk 大小）是可调整的，以便针对不同文档特征进行微调
4. 作为知识库使用者，我希望检索时返回的是完整的文档节（`####` 块全文），而不是被切碎的句子片段，以便获取完整上下文
5. 作为知识库使用者，我希望每个检索结果附带元数据——来自哪个文件、哪个章、哪个节、节标题，以便判断来源的可信度和适用范围
6. 作为数据工程师，当我向已有向量库中添加新版本的同源文档时，希望脚本自动识别哪些节是新增的、哪些已存在但内容有变化、哪些完全未变，仅对需要更新的部分执行向量化
7. 作为数据工程师，当我的 Markdown 使用 `###`/`####` 标题层级时，希望脚本自动推导章-节父子关系；当文档只有 `####` 时，希望可以通过外部映射文件补充章分类信息
8. 作为数据工程师，当我不确定用法时，希望执行 `-h` 能看到完整的参数说明
9. 作为开发者，我希望嵌入模型是可替换的，未来可以切换到其他 SentenceTransformer 模型而不修改代码
10. 作为系统集成者，我希望建库脚本是一个干净的 Python 包，以后可以分别包装为 MCP Server、REST API、或独立 CLI 工具，各自的代码互不耦合

## Implementation Decisions

### 文档模型
- Markdown 标题层级定义文档结构：`####` 标记**节**（检索召回的最小完整单元），`###` 标记**章**（可选父级分类）
- 节的边界：从一个 `####` 标题行开始，到下一个 `####` 标题行或文件末尾结束
- 仅支持 `.md` 输入

### 语义切分策略
- 句子边界：中文按 `。！？；` 拆分，英文按 `. ! ? ;` + 空格拆分
- 对全文档相邻句子对计算 Embedding 余弦相似度，统计均值 μ 和标准差 σ
- 语义转折判定：相邻相似度 < μ - 1.5σ（默认）视为转折点
- 硬边界约束：最小 chunk 3 句（避免碎片），最大 chunk 20 句（避免过长不精准）
- 相似度阈值可通过 `--threshold`（绝对阈值）覆盖自适应行为
- 重叠在切分之后追加：每个 chunk 从尾部向后多取 N 句（默认 2），`--overlap` 可调整

### 父文档检索器
- 小 chunk（语义切分结果）→ 向量索引
- 父文档（整节全文）→ 文档存储
- 同一节内多个 chunk 命中 → 返回去重后的一节
- 使用 LangChain `ParentDocumentRetriever` 实现

### 嵌入模型
- 默认：`paraphrase-multilingual-MiniLM-L12-v2`（SentenceTransformer），支持中英文
- 通过 `--model` 参数可替换为任意 SentenceTransformer 兼容模型
- 向量维度由模型自动适配

### 向量数据库
- 引擎：Chroma
- 距离度量：余弦相似度
- 索引算法：HNSW（Chroma 默认，无需额外配置）
- 存储方式：持久化目录

### 增量更新
- 节唯一标识：`{源文件名(不含扩展名)}#{节编号}`
- 内容哈希：SHA256 对节全文取哈希
- 判定逻辑：ID 存在 + 哈希相同 → 跳过；ID 存在 + 哈希不同 → 删旧插新；ID 不存在 → 插入
- 增量模式下不删除旧数据库中已不存在的节（避免误删其他文档的数据），仅做 upsert

### 元数据 Schema
每个 chunk 携带以下元数据：
- `section_id`：节编号（如 `0101`）
- `section_title`：节中文标题（如 `片剂`）
- `chapter`：所属章名，从 `###` 自动推导，无则为 null
- `source_file`：源文件名（不含扩展名）
- `content_hash`：节全文 SHA256
- `chunk_index`：该节内第几个语义块（0-based）

### 章映射
- 默认：扫描 Markdown，`###` 下属的 `####` 继承章名
- 补充：`--chapter-map` 参数接受 JSON 文件，格式 `{"编号前缀": "章名"}`，如 `{"01": "制剂通则", "04": "光谱法"}`
- 优先级：JSON 映射 > 自动推导 > null

### CLI 接口
- 必需参数：`-i, --input`（目标 Markdown 路径）、`-d, --db`（Chroma 数据库目录）
- 可选参数：`-t, --threshold`、`-o, --overlap`、`--min-chunk`、`--max-chunk`、`--chapter-map`、`-m, --model`
- `-h, --help` 输出简洁参数列表
- 命令名：`rag-build`
- 执行后输出统计：共 N 节，M 个 chunk，插入 X、跳过 Y、更新 Z

### 目录结构
```
rag/
├── src/rag_builder/          # 核心建库包
│   ├── cli.py                # CLI 入口
│   ├── chunker.py            # 语义切分
│   ├── embedder.py           # 嵌入模型封装
│   ├── vector_store.py       # Chroma 操作
│   ├── document.py           # Markdown 解析
│   └── config.py             # 默认参数
├── servers/                  # 未来服务形态
│   ├── mcp/                  # MCP Server
│   ├── api/                  # REST API
│   └── tool/                 # 独立 CLI 工具
├── scripts/                  # 历史数据清洗脚本
├── tests/
├── pyproject.toml
└── README.md
```
`servers/` 下的各模块独立引用 `rag_builder` 包，互相之间无耦合。

## Testing Decisions

### 测试原则
- 只测外部行为，不测实现细节
- 每个测试用临时文件/临时目录，测试结束自动清理
- 使用小型手工编写的 Markdown fixture（~10-20 行），不依赖真实药典大文件

### 测试层级

| 接缝 | 测试内容 | 输入 | 断言 |
|------|---------|------|------|
| 文档解析 | `####` 节边界正确识别 | 多节 mini .md | 返回的 Section 数量、标题、编号正确 |
| 文档解析 | `###` → `####` 章-节关系推导 | 含两层标题的 mini .md | Section.chapter 字段正确继承 |
| 文档解析 | 无 `###` 时章为 null | 仅含 `####` 的 .md | 所有 Section.chapter 为 null |
| 语义切分 | 转折点切分 | 内容差异明显的连续段落 | chunk 数量 > 1，边界在段落交界处 |
| 语义切分 | 最小 chunk 约束 | 全是短句的 Section | 每个 chunk ≥ 3 句 |
| 语义切分 | 最大 chunk 约束 | 全是长段落无转折的 Section | 每个 chunk ≤ 20 句 |
| 语义切分 | 重叠正确追加 | 正常切分结果 | chunk[i].tail == chunk[i+1].head（重叠部分） |
| 向量库写入 | 写入后可检索 | 2 节 mini .md | 查询相关词能返回对应节 |
| 向量库写入 | 元数据完整 | 任意 chunk | 所有 6 个元数据字段非空/正确 |
| 增量更新 | 同内容跳过 | 入库两次同一文件 | 第二次 skip count = 总节数，无重复 |
| 增量更新 | 修改内容更新 | 第一次入库 → 修改一节 → 第二次入库 | update count = 1 |
| 增量更新 | 新节插入 | 第一次入库 → 文件新增一节 → 第二次入库 | insert count = 1 |
| CLI 端到端 | 完整流水线 | `-i mini.md -d tmp_db` | exit code 0，Chroma collection 存在且可检索 |
| CLI | help 输出 | `-h` | 返回码 0，stdout 包含所有参数说明 |

### 测试依赖
- Chroma 支持内存模式或临时目录，不依赖外部服务
- 嵌入模型测试使用轻量级 mock 或固定向量，避免下载大模型
- pytest + tmp_path fixture 处理临时目录

## Out of Scope

- **检索/查询功能**：本脚本只管建库。查询由外部的 MCP Server / API / Tool 负责
- **非 Markdown 输入**：PDF、Word、纯文本等格式暂不支持，需用户自行转换为 Markdown
- **前端 UI**：不提供任何图形界面或 Web UI
- **多文档联合检索**：每个 Chroma 数据库对应一个或多个 Markdown 文件，不处理跨库联合查询
- **权限/认证**：Chroma 数据库为本地目录，不涉及网络访问控制
- **分布式部署**：单机运行，不考虑集群或分布式向量数据库
- **全文搜索/混合检索**：不做 BM25 等关键词检索，纯语义向量检索
