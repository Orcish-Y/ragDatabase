# ADR-0001: 语义切分 + 父文档检索器

| 字段 | 值 |

| 状态 | Accepted |

## 背景

构建通用 RAG 知识库脚本，目标文档为中文 Markdown（如药典），需要将文档索引到 Chroma 向量数据库，支持语义检索。检索结果应返回完整章节而非碎片化文本。

## 决策

### 1. 语义切分替代固定大小切分

**选择**: 利用 Embedding 计算相邻句子相似度，在语义转折点切分，配合最小/最大 chunk 大小约束和重叠。

**替代方案**:
- **固定 Token 数切分**: 最常见做法，LangChain `RecursiveCharacterTextSplitter`。优点：实现极简。缺点：常在语义不完整处切断，中文药典条目结构（编号列表+释义段落）会被截断。
- **按 `####` 节边界切分**: 不做段落级切分，每节一个 Chunk。优点：边界干净。缺点：长节（如 `0101 片剂` 126 行）单个向量难以精确匹配细粒度查询。
- **混合方案**: 短节不切，长节做语义切分。优点：灵活。缺点：增加实现复杂度，行为不一致。

**选择理由**: 语义切分是唯一能做到"在内容自然转折处分段"的方案。对药典类文档尤其重要——例如 `0101 片剂` 下面依次讲含片、舌下片、分散片等，语义切分能将它们各自成块，检索"分散片崩解要求"时能精准匹配到对应段落。

### 2. 父文档检索器 (Parent Document Retriever)

**选择**: 语义 Chunk 存入向量索引，检索匹配后返回所属 `####` 整节全文。

**替代方案**:
- **直接返回 Chunk**: 用户看到的只有几百字的碎片，缺少上下文，不知道这段话出自哪个条目。
- **返回 Chunk + 元数据引用**: 返回碎片 + 节标题，用户自行翻阅原文。缺点：多一步操作，体验差。

**选择理由**: 药典的权威性要求每次引用都能追溯到完整上下文。一个 Chunk 说"崩解时限应符合要求"，用户需要知道这是针对片剂、胶囊剂还是丸剂的规定。父文档检索器保证这个上下文永远完整。

### 3. 重叠发生在切分之后

**选择**: 先找到干净语义边界切分，再让每个 Chunk 尾部多取 N 句作为重叠区域。

**替代方案**:
- **滑动窗口切分**: 边滑动边判断，窗口天然重叠。缺点：语义边界判断受窗口内冗余内容干扰。

**选择理由**: 语义转折点判定应该基于"干浄"的相邻句子对，不应该受窗口内已包含的前后句影响。先切干净再加重叠，两种需求解耦。

## 后果

- **建库时间**: 语义切分需为整份文档计算句子 Embedding 和相似度矩阵，对大文档（如药典 5MB）需要数十秒到数分钟的预处理时间。可接受——建库是一次性或低频操作。
- **向量库不可迁移**: 切换切分策略（如改变阈值、重叠数、最小/最大 chunk）意味着旧的向量库与新 chunk 不兼容，需要重建。这是一个不可逆的参数选择——一旦建库运行起来，阈值应保持稳定。
- **父文档检索器假设 `####` 边界可靠**: 如果 Markdown 格式不规范（标题层级混乱），父文档边界会错误。需在建库阶段做格式校验并报错。
- **Chroma ID 约定是增量更新的前提**: `{文件名}#{节编号}` 的 ID 格式要求节编号在单次处理中唯一且稳定。如果文档重新编号（如 `0101` 变成 `0201`），会被视为新节而重复插入。
